# BillSplit — Java / Jakarta Servlet / Oracle Edition

BillSplit is a web-based group-expense splitter. This edition migrates the application to a **Java 17 + Jakarta Servlet 6.0 + JDBC + Oracle SQL** backend, with a **vanilla HTML/CSS/JavaScript** frontend.

The migration project is in `Billsplit AI/`. The original Node.js/React/PostgreSQL project in `Billsplit orginal/` is a separate source project and should be kept unchanged.

> **Current verification status:** The project has previously been packaged successfully as `target/billsplit.war`, and the included automated tests ran without reported failures (one test was skipped). That verifies compilation/package and the tests that do not require a live Oracle database. It does **not** prove that the Oracle schema, JDBC queries, or every browser workflow works against a configured database. Complete the live-Oracle checks below before treating the migration as fully verified.

## Features

- Sign up with username, email, and password; log in with username and password.
- Store password hashes using BCrypt rather than storing plaintext passwords.
- Maintain a server-side HTTP session using a session cookie.
- Create trips and list trips belonging to the signed-in user.
- Add an existing registered user to a trip by username.
- Record trip expenses, including the amount, note, date, who paid, and how the expense is split.
- Support equal splitting and custom share amounts through the user interface.
- View expense history and calculated settlements for trip members.
- Request an optional AI-generated trip-spending summary using Google Gemini.
- Start the web application and check its health endpoint without Oracle credentials configured; database-backed features require a working Oracle connection.

## Oracle database setup

The schema script is `database/oracle-schema.sql`.

### 1. Install and start Oracle

Install Oracle Database XE (or use a compatible Oracle instance) and make sure its listener and pluggable database are running. The example connection strings in this project use the service name `XEPDB1`; change the URL if your local Oracle installation uses a different service name.

### 2. Create a schema user

Connect as an Oracle administrator and create a dedicated application schema. Choose your own strong password; do not copy a sample password from documentation.

Example SQL (run as a DBA, changing the password yourself):

```sql
CREATE USER billsplit IDENTIFIED BY "CHOOSE_YOUR_OWN_STRONG_PASSWORD";
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE, CREATE VIEW TO billsplit;
ALTER USER billsplit QUOTA UNLIMITED ON USERS;
```

If your organization or Oracle installation uses different tablespaces or policies, adjust the quota and grants accordingly. Use a dedicated application schema rather than the `SYS` or `SYSTEM` account.

### 3. Create the tables

Connect as the new schema user and run the contents of:

```text
database/oracle-schema.sql
```

The script creates the tables and indexes used by the application. It uses Oracle identity columns and Oracle types such as `NUMBER`, `VARCHAR2`, and `TIMESTAMP`.

**Run the schema script once for a fresh schema.** If you run it again after the tables already exist, Oracle will report that the objects already exist. Do not drop existing tables unless you intentionally want to delete their data.

### 4. Verify the schema

After running the script, confirm that these tables exist in the application schema:

- `USERS`
- `TRIPS`
- `TRIP_USERS`
- `TRANSACTIONS`
- `TRANSACTION_USERS`

The database integration test and application workflows should be checked against this exact schema.

## Configuration

Never commit real database passwords or API keys. The project supports environment variables and an external properties file.

### Environment variables

| Variable | Required? | Meaning |
|---|---|---|
| `BILLSPLIT_DB_URL` | Yes for DB-backed workflows | Oracle JDBC connection URL |
| `BILLSPLIT_DB_USER` | Yes for DB-backed workflows | Application schema username |
| `BILLSPLIT_DB_PASSWORD` | Yes for DB-backed workflows | Application schema password |
| `GEMINI_API_KEY` | Optional | Enables Gemini trip summaries |
| `BILLSPLIT_CONFIG` | Optional | Path to a properties file |

Example for a local Oracle service named `XEPDB1`:

```sh
export BILLSPLIT_DB_URL='jdbc:oracle:thin:@//localhost:1521/XEPDB1'
export BILLSPLIT_DB_USER='billsplit'
export BILLSPLIT_DB_PASSWORD='YOUR_REAL_PASSWORD'
# Optional; only needed for AI summaries:
export GEMINI_API_KEY='YOUR_GEMINI_API_KEY'
```

Replace placeholder values with your own settings. Do not paste actual secrets into source code, README files, GitHub issues, screenshots, or chat messages.

Environment variables take precedence over Java system properties with the same environment-variable names, which in turn take precedence over values from the properties file.

### Properties file alternative

The example template is:

```text
config/application.properties.example
```

For local development, copy it to `config/application.properties` and replace the placeholders:

```sh
cp config/application.properties.example config/application.properties
```

The local `config/application.properties` file is ignored by Git. Confirm this before committing:

```sh
git check-ignore config/application.properties
```

The configuration loader also supports:
- a custom path supplied in `BILLSPLIT_CONFIG`, or
- `$CATALINA_BASE/conf/billsplit.properties` when no custom path is supplied.

For example, a properties file uses these keys:

```properties
db.url=jdbc:oracle:thin:@//localhost:1521/XEPDB1
db.user=billsplit
db.password=YOUR_REAL_PASSWORD
gemini.api.key=
```

The literal values beginning with `YOUR_` are treated as placeholders and ignored by the loader. Keep real values only in your local ignored configuration or an appropriately protected external configuration file.

**Important:** The current source archive may contain a local `config/application.properties` file from the developer's machine. Do not publish that file. It should remain untracked and excluded from Git.

## Run locally with Tomcat

### 1. Build the WAR

From `Billsplit AI`:

```sh
mvn clean package
```

### 2. Deploy it

Copy the generated WAR into Tomcat's `webapps` directory:

```sh
cp target/billsplit.war /path/to/apache-tomcat-10.1/webapps/
```

Replace `/path/to/apache-tomcat-10.1` with the actual location of your Tomcat installation. If Tomcat is already running, it normally deploys the WAR automatically; otherwise start Tomcat.

### 3. Configure the environment for Tomcat

The environment variables must be available to the Tomcat process itself. Setting them in one Terminal window does not configure a Tomcat process that was already started from another window or by another service.

For a simple local test, stop Tomcat, set the variables in the same Terminal session, and start Tomcat from that session:

```sh
export BILLSPLIT_DB_URL='jdbc:oracle:thin:@//localhost:1521/XEPDB1'
export BILLSPLIT_DB_USER='billsplit'
export BILLSPLIT_DB_PASSWORD='YOUR_REAL_PASSWORD'
# Optional:
export GEMINI_API_KEY='YOUR_GEMINI_API_KEY'

cd /path/to/apache-tomcat-10.1
./bin/catalina.sh run
```

Use `./bin/catalina.sh run` while diagnosing startup so Tomcat logs remain visible in the Terminal. For normal background operation, use the appropriate Tomcat start/stop scripts.

Alternatively, place `billsplit.properties` under Tomcat's `conf/` directory and ensure the configuration loader can read it. Protect that file from public access and source control.

### 4. Open the application

```text
http://localhost:8080/billsplit/
```

The context path is `/billsplit` because the WAR is named `billsplit.war`.

## Health endpoint and troubleshooting

Open this URL after deploying:

```text
http://localhost:8080/billsplit/api/health
```

The health endpoint does not require a login or database connection. It reports configuration flags, not a full database connectivity check. A typical unconfigured response looks like:

```json
{
  "status": "ok",
  "databaseConfigured": false,
  "geminiConfigured": false
}
```

The values change according to the settings visible to the Tomcat process.

| Symptom | What to check |
|---|---|
| Tomcat welcome page appears instead of BillSplit | Confirm `target/billsplit.war` is in the correct Tomcat `webapps/` folder and open `/billsplit/`, not just `/`. |
| `/billsplit/` returns 404 | Check Tomcat startup/deployment logs and confirm the WAR filename/context path. |
| Health reports `databaseConfigured: false` | Confirm the URL, username, and password are all set in the environment or loaded properties file. |
| Login/signup or other DB-backed actions return HTTP 503 | Configure Oracle, create the schema, run the SQL script, and restart Tomcat with the configuration loaded. |
| Oracle connection fails | Confirm Oracle is running, the service name and port are correct, and the user/password are valid. |
| AI summary says it is not configured | Set `GEMINI_API_KEY` in the Tomcat process environment or `gemini.api.key` in the external properties file. |
| AI summary fails despite being configured | Check the key, network access, Gemini API availability, and Tomcat logs. The application returns a generic failure message for API/network errors. |
| Browser shows stale frontend changes | Hard-refresh the page after rebuilding/redeploying the WAR. Verify the deployed WAR is the latest build. |

If a deployment fails, inspect Tomcat's `logs/` directory, especially `catalina.out` where available and the dated Catalina logs. Do not post logs that contain credentials or tokens.

## Application workflows

1. **Sign up or log in.** New users provide a username, email, and password. Signup requires a password of at least eight characters in the client and should also be validated server-side. Login uses the username and password.
2. **Create a trip.** A signed-in user can create a trip and see trips they belong to.
3. **Add a member.** Add an already registered user using that person's username. The person must already have an account.
4. **Add an expense.** Enter an amount and note, choose the participants, identify who paid, and choose equal or custom split amounts.
5. **Review history and settlements.** The app displays the trip's expense history and calculates suggested transfers based on recorded paid/owed shares. These are calculated settlement suggestions; they do not move money or mark an actual payment in a banking system.
6. **Request an AI summary.** If Gemini is configured, the server sends the trip expense history to the Gemini API and displays the returned summary. Without a key, the app reports that summaries are not configured.

## HTTP API reference

The API is served beneath `/api`. When deployed to Tomcat, the full local URL prefix is `http://localhost:8080/billsplit/api`.

Requests with JSON bodies should use `Content-Type: application/json`. The browser client sends same-origin requests with credentials so the session cookie is included.

| Method | Endpoint | Authentication | Purpose |
|---|---|---|---|
| `GET` | `/api/health` | Public | Reports app status and whether database/Gemini settings are configured. |
| `POST` | `/api/signup` | Public | Creates a user and starts a session. JSON: `{"username":"...","email":"...","password":"..."}`. |
| `POST` | `/api/login` | Public | Authenticates and starts a session. JSON: `{"username":"...","password":"..."}`. |
| `POST` | `/api/logout` | Public route | Invalidates/logs out the current session. |
| `GET` | `/api/me` | Session required | Returns the current user's identity. |
| `GET` | `/api/trips` | Session required | Lists trips for the signed-in user. |
| `POST` | `/api/trips` | Session required | Creates a trip. JSON includes `name`. |
| `GET` | `/api/trips/{tripId}/users` | Session + trip membership | Lists trip members. |
| `POST` | `/api/trips/{tripId}/users` | Session + trip membership | Adds an existing user. JSON: `{"username":"..."}`. |
| `GET` | `/api/trips/{tripId}/transactions` | Session + trip membership | Returns expense history and calculated settlements. |
| `POST` | `/api/trips/{tripId}/transactions` | Session + trip membership | Creates an expense and its shares. |
| `POST` | `/api/trips/{tripId}/summary` | Session + trip membership | Generates a summary or returns a not-configured/failure message. |

The expense request uses an `amount`, optional `note` and `date`, and a `users` array containing each participant's `id`, `borrow`, and `lent` values. The frontend constructs this payload when you use the expense form. Custom/equal split validation is handled by the service layer.

### Example requests

Signup:

```json
{
  "username": "alice",
  "email": "alice@example.com",
  "password": "choose-a-long-password"
}
```

Login:

```json
{
  "username": "alice",
  "password": "choose-a-long-password"
}
```

Create a trip:

```json
{
  "name": "Goa"
}
```

Add an existing member:

```json
{
  "username": "bob"
}
```

These are request-shape examples only; they do not create users or trips by themselves.

### Authentication and response behavior

- Authentication uses a server-side HTTP session and session cookie, not a JWT.
- Protected API routes return HTTP `401` when there is no authenticated session.
- Trip-specific member and transaction routes check that the signed-in user belongs to the requested trip.
- Validation and application errors are returned as JSON error responses.
- When the database is not configured, database-backed routes cannot perform their normal work; the health endpoint remains available.

## Database model

The schema script creates these tables:

| Table | Role |
|---|---|
| `USERS` | User identity, username/name, email, and BCrypt password hash. |
| `TRIPS` | Trip name and optional start date. |
| `TRIP_USERS` | Many-to-many membership between trips and users. |
| `TRANSACTIONS` | Expense amount, note, trip, and transaction timestamp. |
| `TRANSACTION_USERS` | Per-user `borrow` and `lent` amounts for each expense. |

Primary keys use Oracle identity columns. Foreign keys connect members and shares to their parent rows, and unique constraints prevent duplicate usernames and email addresses.

The application expects the schema in `database/oracle-schema.sql`. If you change table or column names, update the corresponding DAO SQL and tests as well.

## Tests and verification boundaries

The test suite includes checks for:

- BCrypt password hashing and verification.
- Signup/login validation behavior.
- Expense validation.
- Equal-split calculation and handling of rounding remainder.
- Settlement minimization.
- Configuration loading and behavior when Gemini is not configured.
- JSON support and database-configuration failure behavior.
- Oracle connection behavior when connection settings are absent.

The test `OracleConnectionTest.connectsWhenOracleIsConfigured` requires a live configured Oracle database and is skipped when its required database setting is absent.

**A passing `mvn test` without Oracle is not proof that the SQL works against Oracle.** After Oracle is configured, run the live connection test and manually test signup, login, trip creation, adding members, creating equal/custom expenses, history, settlements, logout, and AI summaries if enabled.

## Security notes

- Never commit `config/application.properties`, database passwords, access tokens, or Gemini keys.
- `config/application.properties.example` is a placeholder template, not a usable production configuration.
- Passwords are stored as BCrypt hashes.
- JDBC uses prepared statements for database operations.
- The application uses session-based authentication and an HttpOnly session cookie.
- Trip membership is checked on trip-specific member and expense routes.
- Gemini requests are sent from the server; the API key is not intended to be placed in browser JavaScript.
- The summary feature sends expense history, notes, dates, and participant/share information to the Gemini API when enabled. Do not send sensitive expense notes if you do not want them processed by that external service.
- Use HTTPS and appropriate secure-cookie/session settings before exposing the application beyond local development. The included local Tomcat setup is intended for development, not a production security review.
